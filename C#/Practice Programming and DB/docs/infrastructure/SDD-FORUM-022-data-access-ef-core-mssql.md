## 2. Context & Scope

This spec defines the **persistence layer** for ForumGuard: the EF Core `DbContext`, the MSSQL
schema (table/column names, keys, indexes, defaults, delete behavior), and the data-access
abstractions (`IRepository<T>`, the specific repositories, `IUnitOfWork`, `ISpecification<T>` and its
concrete specifications). It also defines the EF Core migration conventions.

The persistence layer realizes the **Repository + Unit of Work + Specification** patterns from the
project pattern catalog (`CLAUDE.md` §5). It lives in `ForumGuard.Infrastructure` and implements
interfaces declared in `ForumGuard.Domain`.

### Covered

- `ForumGuardDbContext : IdentityDbContext<ApplicationUser, IdentityRole<Guid>, Guid>` with `DbSet`s
  for `ForumThread`, `Comment`, `ModerationDecision`.
- Fluent API mapping for every entity: explicit table & column names, key/index naming
  (`PK_[Table]` / `FK_[Child]_[Parent]` / `IX_[Table]_[Columns]`), `DATETIME2(7)` timestamps with
  `SYSUTCDATETIME()` defaults, `NEWSEQUENTIALID()` GUID PK defaults, enum storage policy, max
  lengths, required relationships and delete behavior.
- Concurrency control on `ModerationDecision` / `Comment` moderation writes.
- `IRepository<T>` (generic CRUD + specification query), `ICommentRepository`,
  `IModerationDecisionRepository`, `IForumThreadRepository`, `IUnitOfWork`.
- `ISpecification<T>` and concrete specifications: `FlaggedPendingReviewSpecification`,
  `PublishedCommentsByThreadSpecification`, `ActiveUsersSpecification`.
- EF Core migration file naming and CREATE/DROP guarding conventions.

### Excluded

- Comment lifecycle / state-transition rules — see **SDD-FORUM-010** (Comment Entity &
  Lifecycle). This spec persists the resulting `Status`; it does not enforce the
  transition graph.
- Comment submission, auto-publish and queue-routing use cases — see **SDD-FORUM-001** (Comment
  Submission & Auto-Publish Flow).
- Moderator review use cases (approve/reject) — see **SDD-FORUM-002** (Moderation Queue &
  Decisions). This spec persists `ModerationDecision` rows; it does not enforce review authorization.
- ML scoring and `ICommentAnalyzer` — see **SDD-FORUM-020** (Comment Analysis).
- Options binding (`ModerationOptions`) — see **SDD-FORUM-023** (Configuration & Options).
- Identity role membership and authorization policies — see **SDD-FORUM-011** (Roles &
  Authorization Model). This spec only owns the Identity schema generated by
  `IdentityDbContext` plus the `ApplicationUser` extension columns (`DisplayName`, `IsActive`,
  `CreatedAtUtc`).

### Related specs

- **SDD-FORUM-001** — Comment Submission & Auto-Publish Flow (writes `Comment` rows).
- **SDD-FORUM-002** — Moderation Queue & Decisions (writes `ModerationDecision` rows; reads the queue).
- **SDD-FORUM-010** — Comment Entity & Lifecycle (canonical entities/enums/state machine).
- **SDD-FORUM-020** — Comment Analysis (writes `AnalysisLabel` / `AnalysisScore` / `AnalyzedAtUtc`).
- **SDD-FORUM-021** — Moderation Pipeline (consumes specifications during the submission flow).

## 3. Behavior

RFC-2119 keywords (MUST / SHOULD / MAY) are used. Every MUST/SHOULD below is independently testable.

### 3.1 Happy path — context, schema and round-trip persistence

- **B-1 (MUST):** `ForumGuardDbContext` MUST derive from
  `IdentityDbContext<ApplicationUser, IdentityRole<Guid>, Guid>` and MUST expose
  `DbSet<ForumThread> ForumThreads`, `DbSet<Comment> Comments`, and
  `DbSet<ModerationDecision> ModerationDecisions`.
- **B-2 (MUST):** `OnModelCreating` MUST call `base.OnModelCreating(builder)` before applying the
  ForumGuard entity configurations, so the ASP.NET Core Identity schema is registered.
- **B-3 (MUST):** Every ForumGuard entity MUST be mapped through a dedicated
  `IEntityTypeConfiguration<T>` class (one configuration class per entity, one class per file). The
  context MUST register them via `builder.ApplyConfigurationsFromAssembly(...)` (or equivalent
  explicit `ApplyConfiguration` calls).
- **B-4 (MUST):** All table and column names MUST be configured **explicitly via Fluent API**. The
  model MUST NOT rely on EF Core naming conventions for ForumGuard tables. Tables MUST be named
  `ForumThreads`, `Comments`, `ModerationDecisions` (no `tbl_` prefix).
- **B-5 (MUST):** Every GUID primary key (`ForumThread.Id`, `Comment.Id`, `ModerationDecision.Id`)
  MUST be configured with a SQL default of `NEWSEQUENTIALID()`. `NEWID()` MUST NOT be used for any
  primary key.
- **B-6 (MUST):** Every audit timestamp (`ApplicationUser.CreatedAtUtc`, `ForumThread.CreatedAtUtc`,
  `Comment.CreatedAtUtc`, `ModerationDecision.DecidedAtUtc`) MUST be column type `DATETIME2(7)` with
  a SQL default of `SYSUTCDATETIME()`. Nullable timestamps (`Comment.PublishedAtUtc`,
  `Comment.AnalyzedAtUtc`) MUST be `DATETIME2(7)` and nullable, with **no** default value.
- **B-7 (MUST):** Primary keys MUST be named `PK_[Table]` (e.g., `PK_Comments`), foreign keys
  `FK_[Child]_[Parent]` (e.g., `FK_Comments_ForumThreads`, `FK_Comments_AspNetUsers`), and indexes
  `IX_[Table]_[Columns]` (e.g., `IX_Comments_ThreadId`).
- **B-8 (MUST):** A clean comment round-trip MUST persist and re-materialize all canonical columns
  with no data loss: inserting a `Comment` with `Status = CommentStatus.Published`,
  `AnalysisLabel = ToxicityLabel.Clean`, a populated `AnalysisScore`, `PublishedAtUtc` and
  `AnalyzedAtUtc`, then reloading it from a fresh context, MUST return identical values.
- **B-9 (MUST):** Inserting an entity that has only its required non-key, non-defaulted fields set
  MUST succeed, and `Id`, `CreatedAtUtc`/`DecidedAtUtc` MUST be populated by the database defaults
  (the application MUST NOT be required to assign them).
- **B-10 (MUST):** `IUnitOfWork.SaveChangesAsync(CancellationToken)` MUST commit all tracked changes
  in a single call and MUST return the number of affected rows. Changes made through repositories
  MUST NOT be persisted until `SaveChangesAsync` is called.
- **B-11 (MUST):** `IRepository<T>` MUST expose at minimum: `GetByIdAsync(Guid id, CancellationToken)`,
  `ListAsync(ISpecification<T> spec, CancellationToken)`, `SingleOrDefaultAsync(ISpecification<T> spec,
  CancellationToken)`, `CountAsync(ISpecification<T> spec, CancellationToken)`, `Add(T entity)`,
  `Update(T entity)`, and `Remove(T entity)`. Mutating members (`Add`/`Update`/`Remove`) MUST NOT call
  `SaveChanges` themselves — committing is the responsibility of `IUnitOfWork`.
- **B-12 (MUST):** `ListAsync` / `SingleOrDefaultAsync` / `CountAsync` MUST apply the supplied
  `ISpecification<T>` (criteria, includes, ordering, paging) before executing against the database.
- **B-13 (MUST):** `ISpecification<T>` MUST expose at minimum a `Criteria`
  (`Expression<Func<T,bool>>`), an `Includes` collection (navigation expressions), and optional
  ordering and paging members. A specification's `Criteria` MUST be composable into an
  `IQueryable<T>` server-side (no client-side evaluation of `Criteria`).
- **B-14 (MUST):** `FlaggedPendingReviewSpecification` MUST select exactly the `Comment` rows whose
  `Status == CommentStatus.FlaggedForReview` (the moderator queue), ordered by `CreatedAtUtc`
  ascending (oldest first). It MUST NOT return `Published`, `ApprovedByModerator`,
  `RejectedByModerator`, or `PendingAnalysis` comments.
- **B-15 (MUST):** `PublishedCommentsByThreadSpecification(Guid threadId)` MUST select exactly the
  `Comment` rows for the given `ThreadId` whose `Status` is `Published` **OR**
  `ApprovedByModerator` (the public-visibility invariant from SDD-FORUM-010), ordered by
  `PublishedAtUtc` ascending. It MUST NOT return hidden statuses (`PendingAnalysis`,
  `FlaggedForReview`, `RejectedByModerator`).
- **B-16 (MUST):** `ActiveUsersSpecification` MUST select exactly the `ApplicationUser` rows whose
  `IsActive == true`.
- **B-17 (SHOULD):** `ICommentRepository`, `IModerationDecisionRepository`, and
  `IForumThreadRepository` SHOULD extend `IRepository<T>` and add only intent-revealing query methods
  (e.g., `ICommentRepository.GetFlaggedQueueAsync`, `IModerationDecisionRepository.GetByCommentIdAsync`)
  that are implemented in terms of the relevant specification, not ad-hoc inline LINQ scattered across
  callers.
- **B-18 (SHOULD):** Enum-typed columns (`Comment.Status`, `Comment.AnalysisLabel`,
  `ModerationDecision.Decision`) SHOULD be stored as `int` (the EF Core default for enums). The chosen
  storage MUST be configured explicitly per column and MUST round-trip the enum value unchanged.

### 3.2 Edge case — delete behavior (cascade vs restrict)

- **B-19 (MUST):** The `Comment → ForumThread` relationship (`FK_Comments_ForumThreads`) MUST be
  configured `DeleteBehavior.Cascade`: deleting a `ForumThread` MUST delete its `Comment` rows.
- **B-20 (MUST):** The `Comment → ApplicationUser` (author) relationship
  (`FK_Comments_AspNetUsers`), the `ForumThread → ApplicationUser` (creator) relationship, and the
  `ModerationDecision → ApplicationUser` (moderator) relationship MUST be configured
  `DeleteBehavior.Restrict`. An attempt to delete an `ApplicationUser` that still authors comments,
  owns threads, or has recorded moderation decisions MUST fail at the database (referential-integrity
  violation) rather than cascade-delete forum content. This protects the author/moderator audit trail;
  account deactivation is performed via `ApplicationUser.IsActive`, not row deletion (see
  **SDD-FORUM-003**).
- **B-21 (MUST):** The `ModerationDecision → Comment` relationship (`FK_ModerationDecisions_Comments`)
  MUST be configured `DeleteBehavior.Cascade`: deleting a `Comment` MUST delete its associated
  `ModerationDecision` rows. (In normal operation comments are not deleted; this rule defines the
  cleanup behavior for the cascade originating from a deleted thread, so a deleted thread removes its
  comments and their decisions without orphaning rows.)

### 3.3 Edge case — concurrency on a moderation decision

- **B-22 (MUST):** `Comment` MUST carry an optimistic-concurrency token (a `rowversion` /
  `[Timestamp]` column mapped via Fluent API, e.g., `IsRowVersion()`). When two moderators load the
  same `FlaggedForReview` comment and both submit a decision, the **first** `SaveChangesAsync` MUST
  succeed and the **second** MUST fail with a concurrency conflict rather than silently overwriting
  the first decision.
- **B-23 (MUST):** When the optimistic-concurrency conflict in B-22 is raised, it MUST surface as a
  `DbUpdateConcurrencyException` out of `SaveChangesAsync`. The data layer MUST NOT swallow it;
  callers (SDD-FORUM-002) MUST be able to translate it into a user-facing "this comment was already
  reviewed" outcome (see §5, E-4).

### 3.4 Edge case — cancellation and not-found lookups

- **B-24 (MUST):** All async repository and `IUnitOfWork` members MUST accept a `CancellationToken`
  and MUST honor cancellation (a cancelled token MUST cause the operation to throw
  `OperationCanceledException` / `TaskCanceledException` rather than completing).
- **B-25 (MUST):** `GetByIdAsync` and `SingleOrDefaultAsync` MUST return `null` when no matching row
  exists; they MUST NOT throw a not-found exception. `CountAsync` MUST return `0` for an empty result
  set.

### 3.5 Migration conventions

- **B-26 (MUST):** EF Core migrations MUST be created for every schema change. The corresponding SQL
  artifact MUST be named `v[X.Y.Z]_[ShortDescription].sql` (e.g., `v1.0.0_InitialSchema.sql`) and MUST
  begin with a versioned header comment that references this spec ID (`SDD-FORUM-022`) and any other
  driving spec IDs.
- **B-27 (MUST):** Every `CREATE`/`DROP` statement in a hand-authored migration SQL artifact MUST be
  guarded with `IF NOT EXISTS` (for `CREATE`) / `IF EXISTS` (for `DROP`) so the script is idempotent.
- **B-28 (MUST):** An already-applied migration MUST NOT be edited in place; a schema change MUST be a
  **new** migration with the next version number.
- **B-29 (SHOULD):** The initial migration SHOULD produce a database that an integration test can
  create, migrate, seed and query end-to-end against MSSQL without manual SQL edits.

## 4. Validation Rules

### 4.1 Field-level

| Field | Rule |
|---|---|
| `ApplicationUser.DisplayName` | Required; mapped as non-nullable; SHOULD have a configured max length (default 256). |
| `ApplicationUser.IsActive` | Required `bit`; default `1` (true) at the database. |
| `ApplicationUser.CreatedAtUtc` | `DATETIME2(7)`, non-nullable, default `SYSUTCDATETIME()`. |
| `ForumThread.Title` | Required; `NVARCHAR(200)` (max 200); MUST reject longer values. |
| `ForumThread.Id` | GUID PK, default `NEWSEQUENTIALID()`. |
| `Comment.Body` | Required; `NVARCHAR(4000)` (max 4000); MUST reject longer values. |
| `Comment.Status` | Required; stored as `int`; non-nullable; defaults to `PendingAnalysis` semantics set by the application (SDD-FORUM-001), not the DB. |
| `Comment.AnalysisLabel` | Nullable `int` (`ToxicityLabel`). |
| `Comment.AnalysisScore` | Nullable `float`/`real`. |
| `Comment.PublishedAtUtc`, `Comment.AnalyzedAtUtc` | Nullable `DATETIME2(7)`, no DB default. |
| `Comment.Id` | GUID PK, default `NEWSEQUENTIALID()`. |
| `ModerationDecision.Decision` | Required; stored as `int` (`ModerationOutcome`). |
| `ModerationDecision.Reason` | Nullable; `NVARCHAR(500)` (max 500). |
| `ModerationDecision.DecidedAtUtc` | `DATETIME2(7)`, non-nullable, default `SYSUTCDATETIME()`. |
| `ModerationDecision.Id` | GUID PK, default `NEWSEQUENTIALID()`. |

### 4.2 Cross-field / relational

- `Comment.ThreadId` MUST reference an existing `ForumThread.Id` (FK `FK_Comments_ForumThreads`,
  cascade).
- `Comment.AuthorId` MUST reference an existing `ApplicationUser.Id` (FK `FK_Comments_AspNetUsers`,
  restrict).
- `ForumThread.CreatedById` MUST reference an existing `ApplicationUser.Id` (restrict).
- `ModerationDecision.CommentId` MUST reference an existing `Comment.Id` (FK
  `FK_ModerationDecisions_Comments`, cascade).
- `ModerationDecision.ModeratorId` MUST reference an existing `ApplicationUser.Id` (restrict).

### 4.3 State-based / index

- `IX_Comments_Status` MUST exist to support the moderator-queue specification
  (`FlaggedPendingReviewSpecification`) efficiently.
- `IX_Comments_ThreadId` MUST exist to support `PublishedCommentsByThreadSpecification`.
- `IX_ModerationDecisions_CommentId` MUST exist to support lookup of decisions by comment.
- The persistence layer MUST persist whatever `CommentStatus` value the domain assigns; it MUST NOT
  re-validate or rewrite the lifecycle transition (transition legality is SDD-FORUM-010's concern).

## 5. Error Rules

| ID | Trigger | Type | Domain mapping | Razor / user-facing outcome |
|---|---|---|---|---|
| **E-1** | Insert/update violates a required-field, max-length, or `int`-enum constraint. | validation | `DbUpdateException` from `SaveChangesAsync`; surfaced to callers. Application-level length checks (SDD-FORUM-001 / SDD-FORUM-023 `MaxCommentLength`) SHOULD catch this earlier as `Result<T>` validation failure. | Submission/edit page redisplays with a field validation message; no row written. |
| **E-2** | Inserting a `Comment`/`ForumThread`/`ModerationDecision` with an FK pointing to a non-existent parent. | notfound / conflict (referential integrity) | `DbUpdateException` (FK violation) from `SaveChangesAsync`. | Operation fails; user sees a generic "the item no longer exists" message; no row written. |
| **E-3** | Deleting an `ApplicationUser` that still authors comments, owns threads, or has moderation decisions (restrict FK). | conflict | `DbUpdateException` (FK constraint) from `SaveChangesAsync`. Account management uses `IsActive` deactivation instead (SDD-FORUM-003). | Admin account page reports the account cannot be deleted; deactivate instead. |
| **E-4** | Two moderators decide the same `FlaggedForReview` comment concurrently (rowversion mismatch). | conflict | `DbUpdateConcurrencyException` from `SaveChangesAsync`; MUST propagate (B-23). | The losing moderator sees "this comment was already reviewed" and the queue refreshes (handled by SDD-FORUM-002). |
| **E-5** | A `CancellationToken` is cancelled mid-operation. | n/a (cancellation) | `OperationCanceledException` / `TaskCanceledException`. | Request is abandoned; nothing persisted. |
| **E-6** | A specification's `Criteria` cannot be translated server-side (would force client evaluation). | validation (developer error) | EF Core `InvalidOperationException` at query execution. | Not user-facing; caught in integration tests (B-13) before release. |

The data layer MUST NOT catch-and-swallow `DbUpdateException`, `DbUpdateConcurrencyException`, or
`OperationCanceledException`; these MUST propagate so the Application/Web layers can map them to
`Result<T>` outcomes or user-facing messages.

## 6. Versioning Notes

- **v1 — Initial specification (2026-06-21).** Defines `ForumGuardDbContext`, the MSSQL Fluent API
  schema (explicit names, `PK_/FK_/IX_` naming, `DATETIME2(7)` + `SYSUTCDATETIME()`,
  `NEWSEQUENTIALID()` GUID PKs, `int`-stored enums), delete behavior (cascade thread→comments→decisions;
  restrict on author/creator/moderator), optimistic concurrency on `Comment`, the
  `IRepository<T>` / specific repositories / `IUnitOfWork` / `ISpecification<T>` contracts, the three
  concrete specifications, and the migration naming/guarding conventions. Greenfield — authoritative.
